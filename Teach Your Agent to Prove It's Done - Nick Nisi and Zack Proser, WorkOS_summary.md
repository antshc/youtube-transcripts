## Executive Summary

This is a one-hour workshop by two WorkOS engineers. It opens with the story of an agent that deleted production databases "in nine seconds". Nick Nisi and Zack Proser use it to show why "the agent says it's done" can't be trusted. Agents write code faster than humans can review it, so reading every line or every PR doesn't scale. Their answer is to stop checking the code and make the agent prove the outcome. They cite a quote attributed to Lauren Tan: *if an agent can't verify its own work, nothing else matters.*

The mechanism is a deterministic, app-specific verification loop. The team builds a small CLI, which the demo calls `snack`, that lets an agent start the app, drive it, inspect its network, storage, console and screenshots, and run a "prove" command. The agent loops on that command until it passes, and a failure feeds the next attempt. In the demo, a waitlist form shows "success" in the UI but never persists the email. A UI-only check passes, while the CLI's storage check exposes the bug.

The speakers treat this as foundational:

- **Velocity:** the tooling lets one person run 10–30 parallel agent lanes. The goal is to come back to finished work rather than nudging each agent turn by turn.
- **Team benefit:** the gains accrue to the whole team, not just the author.
- **Receipts:** every run's evidence (screenshots, receipts, journeys) is valuable data. It becomes the baseline for evals and for future self-improving ("RSI") code bases.
- **Outcomes over procedures:** give agents clear outcomes and a way to check them rather than step-by-step instructions, because modern frontier models do better when given the goal and the freedom to find the path.

Caveats are repeated. A screenshot isn't proof, and a model-based "judge" can disagree with literal checks. Tools can't be generic and must be built per app. Trust is a gradient built up over time, not a switch.

## Core Theses: Deep Insights and Real-World Anchors

### "If an agent can't verify its own work, nothing else matters."
**Meaning:** Verification is the bottleneck for agent autonomy. It matters more than prompting skill or model choice.
**Why:** For every detail you don't specify, the model infers something, and its assumptions may not match yours. LLMs are "trying to make you happy", so they produce confident confabulations.
**Examples from the talk:**
- A waitlist form displays "success", but the email isn't persisted, and a reload shows an empty list (05:16–06:25).
- "It builds, it runs, the tests pass, and it's still wrong" (07:03).
- The Riker/CTX tools refuse to mark a workflow node satisfied until the GitHub API confirms the PR exists and its checks pass (13:33–13:55).

**Caution:** Trust isn't zero or one. They frame it as "a gradient" that you push toward one.

### "Status comes from records, not model prose."
**Meaning:** Demand receipts: screenshots, videos, test results, smoke tests, API-verified facts. Don't accept the agent's narration of success.
**Examples:**
- CTX is a centralized verification web service. The agent reports "I'm done, please verify", an evaluator runs a known verifier, and only then is the node marked satisfied (13:16–13:55).
- Riker babysits PRs: it builds a check, runs the tools, keeps the evidence, and decides when to stop (15:55–16:10).
- Attaching screenshots and walkthrough recordings to PRs, so you can watch the flow before reading any code (24:27–24:35, 51:56–52:13).

**Caution:** "A successful screenshot isn't proof". It may show a state reached by a path no user could take, so run the real flow start to finish (31:17–31:48).

### "Move the human's verification habits into a deterministic CLI."
**Meaning:** Humans verify a web app by reloading, checking the network tab, console, storage and page content. Encode those checks as commands. A vague prompt like "always verify in a browser" is interpreted differently by each run.
**Why:** A single command backed by real bash calls is more uniform than 30 agents given the same paragraph. It feeds exact output back so the agent knows what's wrong, and it can be rerun forever as a regression check.
**Examples:**
- `snack` provides up/down/doctor, drivers (join, reload, reset), observers (snapshot, network, storage, console, screenshot) and `prove`/`judge` (20:43–21:38).
- The doctor check validates node, Chromium, the session and the build (36:07–36:17).
- Extrapolation, not stated: other teams might encode API contract checks or database assertions the same way. The speakers only say it is app-specific (27:31–27:41).

**Caution:** They don't ship a universal tool because there isn't one. Each team has to build the CLI and the evals for its own app (27:31–28:03).

### "Give the map, not the turn-by-turn directions."
**Meaning:** Outcome-driven development. Say where the agent must end up and how it will know it's there, without prescribing the route. Over-prescription can lower performance.
**Why:** With the right constraints, "constraints can equal freedom". Agents then take detours that catch edge cases or ask unlocking questions. They say this is only reliably true of the latest frontier models (33:35–35:06).
**Examples:**
- "You must get here; you'll know you're here when this command returns this" (34:12–34:16).
- Decomposing work into small tasks, each with an explicit definition of done, rather than a days-long mega-session on a giant PR (10:28–10:51).
- The workshop repo's [feature map](https://github.com/workos/beyond-done/blob/main/lab/verify/features/waitlist.md) is a short file the agent reads first. It lists what exists, how a user reaches it, how to drive it, the contract to meet, and what usually lies. It doesn't say how to fix the app. This comes from the repo, not the talk.
- Extrapolation: a bug-fix prompt would state the failing check to turn green and leave the code path to the agent.

**Caution:** They aren't trying to wrap determinism around the LLM. Determinism is for the checks, and creativity is for the solving.

### "Failures should drive the next loop."
**Meaning:** A durable verify loop makes the agent self-heal. On failure it retries and re-verifies without you. The reasoning is red/green/refactor applied to agents: reproduce, show it, fix, show the proof (35:09–35:45).
**Examples:**
- In the demo, `storage` returns empty after `join`, so the agent knows "I am not done" and fixes persistence (36:38–37:07).
- Explicit, detailed **error messages** are more valuable now, because agents interpret them well and self-heal (32:41–33:21).
- Feedback-loopable output such as printing a bouncing ball's coordinates reveals a teleport bug even without seeing the canvas (28:20–29:11, described as an Amp-team example).

**Caution:** Self-healing only works if the checks actually test the real outcome.

### "Receipts today are the eval dataset of tomorrow."
**Meaning:** Persist every run's evidence: user journeys, errors, timings, flows. They can feed LLMs now for fixes. In the future they become evals that agents "hill-climb" on in self-improving setups (37:57–39:08, 50:56–52:56).
**Examples:**
- An overnight agent aggregates receipts ("eight failures in the caching module"), opens a fix PR, and proves the issue is fixed (51:19–51:42).
- An e-commerce journey record: login, catalog load time, cart, abandonment (51:01–51:15).
- Once verifiers exist, the source language matters less. You can re-implement the app (rewrites to Rust or Go are mentioned) and prove it still works (22:08–22:50).

**Caution:** The competitive-advantage claim ("if your competitors sit on a mountain of this data, they go faster", 52:35–52:55) is the speakers' opinion.

### "Deterministic checks and a model judge catch different failures."
**Meaning:** `prove` uses Playwright-style assertions. `judge` uses a fast ("system one") model to assess whether the outcome meets the intent without brittle text matching. In the repo, `judge` calls TypeSafe's System One model, Jev ([TypeSafe blog post](https://typesafe.ai/blog/introducing-system-one-models-and-jev)). In the demo the page said "waitlisted" while the confirmation text said "you're in, your seat is confirmed" (a contract mismatch), and the judge flagged it (39:11–40:14).
**Examples:**
- The "saboteur/detective" game injects a random bug. The detective must name the bug using only `snack` and give proof. Outcomes include named correctly, over-promised, blamed a bug that wasn't there, or found nothing (41:45–42:11, 45:25–47:12).
- "No bug found" is a valid answer (47:08).

**Caution:** The mismatch the judge found was a contrived example, and the speakers note their own demo output needed debugging (45:16–45:23). Receipts also go stale when code changes (47:24–47:40).

## Easy-Recall: Actionable Insights for Practice

**Principles**
- Don't read every line or PR. Verify the outcome the user sees.
- Every unspecified detail gets guessed by the model, so define the goal and a way to check it.
- Demand evidence, not narration.

**Build**
- If a web app has no custom verifier CLI, build one first. They call it one of the highest-leverage steps.
- Expose app lifecycle commands (up, down, doctor), drivers (act in the app), observers (network, storage, console, screenshot) and a `prove` command.
- Give agents "eyes and arms", such as Chrome DevTools for web. Native or iOS apps need equivalents.
- Make the verifier output detailed state so the agent can audit it.
- Write explicit, detailed error messages. Agents act on them.
- Add a model-based judge alongside deterministic proofs. It catches meaning-level mismatches that literal assertions miss, but keep the unit tests as a drift check.

**Workflow**
- Decompose into small tasks, each with a definition of done and a verification command.
- Avoid one agent session running three or four days on a giant PR.
- Loop: reproduce, show it, fix, show proof, then rerun everything for regressions.
- If you juggle many agent lanes, aim to return to work that is already done, not to nudge turn by turn.
- Attach screenshots, recordings and walkthroughs to PRs so a human can watch before reading code.

**Pitfalls**
- A screenshot alone isn't proof. Ensure the state was reached via real steps.
- UI-only checks miss persistence (the "lost email" bug).
- Stale receipts can describe code that no longer exists.
- Greptile 5/5 plus green CI can still allow 10,000 lines of nothing (58:59–59:10), so you still need outcome verification.
- Don't be overly prescriptive about how the agent solves it.

**If-then guidance**
- If you want a team-wide default, put verification instructions in `AGENTS.md` (the speaker prefers it to `CLAUDE.md`). Hooks are also shareable (55:05–55:36).
- If you don't want the check to depend on the model following a skill, enforce it in CI. One audience member leaned away from skills for this reason (53:50–54:06).
- If you deploy agent-built changes, consider preview first, then production, with an agent watching metrics, feature flags and Datadog, and reverting if it looks bad (59:55–60:26).

**Memorable phrases**
- "Show me the receipts."
- "Status comes from records, not model prose."
- "Gardening multiple code bases and letting them self-evolve."
- "Tools give your agent its body; the LLM is the brain."
- "Mount and climb the evidence ladder."
